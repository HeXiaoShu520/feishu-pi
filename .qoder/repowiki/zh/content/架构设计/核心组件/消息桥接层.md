## 简介
本章节面向"消息桥接层"，聚焦于将飞书消息与智能体会话进行双向转换的机制。重点包括：
- **FeishuAgentBridge**：负责入站消息到会话提示、事件流到卡片渲染、指令处理与状态收尾，现已集成全新的 ReplyParts parts-based 架构。
- **LarkTransport**：基于飞书底层 WSClient + EventDispatcher 的长连接传输，负责消息归一化、上下文提取、话题收敛、附件下载与卡片回调。
- **ReplyParts**：全新的回复正文 parts 模型，支持精简模式滚动回收和详细模式全量保留，提供高性能的段落管理。
- **CardKitReply**：基于 CardKit 的流式回复包装器，支持自动分卡和降级机制。
- 会话管理：ConversationManager 保证同一会话内顺序执行、并发打断与持久化恢复。
- 卡片流式更新：CardKitStream 提供高性能流式卡片渲染、节流与错误恢复。
- 可靠性：MessageStore 实现消息去重与失败保护；ReactionController 提供处理中表情反馈。
- 安全与权限：管理员校验、模型切换限制、文件名清洗等。

## 项目结构

## 核心组件
- **LarkTransport**：建立并维护飞书 WebSocket 长连接，注册事件分发器，归一化消息，构造上下文，处理卡片回调，支持附件下载与卡片更新。
- **FeishuAgentBridge**：订阅传输层消息，解析指令，创建 CardKit 流式卡片，调用 ConversationManager 发起会话提示，使用 ReplyParts 管理回复内容，根据事件流更新卡片正文与小字统计，最终关闭卡片并记录日志。**已集成 ReplyParts parts-based 架构**。
- **ReplyParts**：全新的 parts-based 回复系统，支持精简模式滚动回收和详细模式全量保留，提供高性能的段落管理和终态组装。
- **CardKitReply**：基于 CardKit 的流式回复包装器，支持自动分卡、降级机制和线程回复策略。
- **ConversationManager**：按 conversationId 管理会话，串行执行 prompt，支持新消息打断在途请求，持久化 session 文件以保障中断恢复。
- **CardKitStream**：封装飞书 CardKit v1 流式卡片 API，提供增量更新、替换、统计小字写入、流式模式开关与自动重试。
- **MessageStore**：基于 JSON 存储的消息处理状态机，防止重复投递与重复执行。
- **ReactionController**：在处理消息时添加随机表情，完成后移除，提升交互体验。
- **LarkImageProcessor**：下载图片/附件并转换为 Pi 可用格式，支持本地缓存与 MIME 检测。

### LarkTransport：WebSocket 连接管理、消息路由与上下文提取
- 连接管理：使用 WSClient + EventDispatcher 注册 im.message.receive_v1 与 card.action.trigger 事件；内置握手超时、ping 超时、重连与错误日志。
- 消息路由：normalize 归一化消息，过滤机器人自身消息，构造 conversationId（私聊/群聊/话题群），下载图片与附件，清理 @机器人 标记，记录用户输入日志。
- 上下文提取：获取用户 profile（openId、名称、部门），判断管理员身份，组装 FeishuContext（含 conversationId、chatId、threadId、isAdmin）。
- 卡片回调：解析 value（对象或 JSON 字符串），授权卡回调转交上层处理器；非管理员点击模型切换卡片返回拒绝提示；管理员切换后持久化模型名并更新卡片。
- 会话模式缓存：查询 chat_mode（p2p/group/topic），用于话题群会话收敛策略。
- 资源下载：统一将 image/file/audio/video/media 等资源下载为 Buffer，保存到本地缓存目录，并在消息文本中追加路径提示。

### ReplyParts：parts-based 回复系统

**全新组件** 实现了完整的 parts-based 架构，替代了之前的临时文本机制。

- **核心设计**：
  - parts 数组存储正文段和工具摘要段，toolPartIndices 记录工具段位置
  - 支持两种模式：精简模式（滚动回收）和详细模式（全量保留）
  - 通过 ReplyPartsSink 接口解耦内容生成与推送逻辑

- **精简模式滚动回收**：
  - 新正文段出现时，旧工具段与旧正文全部置空，只保留"最新正文段"
  - 新工具段出现时，上一个工具段就地置空（只留当前一个）
  - 避免长任务刷屏，提升用户体验

- **详细模式全量保留**：
  - 所有段落原样保留，完整执行链路可审查
  - 适合调试和审计场景

- **智能增量更新**：
  - 同一段落内的增量文本只推送 delta，避免重复渲染
  - 新段落出现时根据模式选择 render 或 append

- **终态组装**：
  - 详细模式：返回全量内容
  - 精简模式：返回最后一个工具段之后的正文（无则退回全部非工具段）
  - 保证已见内容不丢、结论完整可读

### FeishuAgentBridge：消息到会话的转换与卡片渲染

**已更新** 集成了全新的 ReplyParts parts-based 架构，提供更强大的回复管理能力。

- **入站消息处理**：
  - 去重：通过 MessageStore.claim 避免重复执行 Agent。
  - 指令识别：匹配 /new、/stop、/detail 等指令，执行相应逻辑并发送卡片回复。
  - 表情反馈：开始处理时添加随机 reaction，完成后移除。
  - **ReplyParts 集成**：创建 ReplyParts 实例，绑定 CardKitReply 作为 sink，根据 detailMode 动态判断模式。
  - 会话提示：调用 ConversationManager.prompt，传入文本、图片与完整上下文。
  - **事件流处理**：
    - assistant_text：首次真实内容到达时停止动画，清空累积器，通过 replyParts.appendText 增量推送。
    - tool_started/tool_finished：通过 replyParts.appendTool 追加工具摘要段，精简模式下自动滚动回收；小字位置同步工具动画。
  - 收尾：**增强** 计算本次新增 token、成本、耗时、上下文占用百分比，使用 formatStatsLine 格式化统计小字，通过 replyParts.composeFinal() 获取最终内容，关闭卡片，记录响应日志，标记消息完成。
- 错误处理：**已增强** 捕获异常，标记消息失败，关闭卡片并上抛原始错误，确保资源正确释放。
- 命令卡片发送：直接调用飞书消息接口发送 interactive 卡片，附带幂等 uuid。

**关键改进**：
- **ReplyParts 集成**：完全替代了之前的临时文本机制，提供更灵活的段落管理
- **资源泄漏防护**：在 try-finally 块中确保 animationTimer 和 toolTimer 的正确清理
- **类型安全**：改进 token 统计计算，使用类型断言确保数据完整性
- **错误一致性**：统一的错误处理和资源清理机制

### CardKitReply：流式回复包装器与分卡策略

**已更新** 增强了分卡策略和错误处理机制。

- **创建卡片**：POST /open-apis/cardkit/v1/cards，启用 streaming_mode。
- **增量更新**：PUT elements/content，带 sequence 与 uuid，内部节流最小间隔，避免频繁请求。
- **替换与临时文本**：replace 覆盖全文；showTransient/clearTransient 附加临时文本（如工具调用行），避免闪烁。
- **统计小字**：独立元素更新 stats。
- **关闭流程**：等待客户端渲染完成，写入统计小字，关闭流式模式，最终内容不再覆盖正在渲染的文本。
- **自动分卡**：当正文超过 maxCardChars（默认 10000）时，在安全的块边界（段落空行且不在代码围栏内）切分，旧卡流式收尾，新卡继续承载剩余内容。
- **错误恢复**：**已增强** 官方约 10 分钟会关闭流式模式，PUT 失败时尝试重新开启并重试一次，提高稳定性。
- **线程回复策略**：根据 chatMode 和 threadId 智能决定是否在话题中回复。

### ConversationManager：会话队列、中断与持久化
- 会话复用：按 conversationId 获取或初始化会话状态，合并并发首次初始化。
- 顺序执行：每个会话维护一个 Promise 队列，确保消息顺序执行。

## 性能与可靠性
- **流式渲染性能**：
  - CardKitStream 支持可配置的 printFrequencyMs（默认 30ms）与 printStep（默认 3），加快客户端打字机渲染。
  - 节流最小间隔（默认 800ms）减少网络请求频率。
  - **ReplyParts 优化**：同段落增量只推送 delta，避免重复渲染；精简模式滚动回收减少内存占用。
  - 临时文本与正文分离，避免并发 patch 导致的闪烁。
- **连接可靠性**：
  - WSClient 自带重连机制，提供 onReconnecting/onReconnected/onError 日志。
  - 卡片流式模式可能被关闭，CardKitStream 自动重试重新开启。
- **消息去重与失败保护**：
  - MessageStore 基于 TTL 的 processing 状态，避免重复执行与卡住任务。
  - 错误路径标记 fail，防止立即重试风暴。
- **会话中断与恢复**：
  - ConversationManager 支持新消息打断在途请求，并在首个 message_end 落盘后立即持久化映射，确保中断后可恢复。
- **资源下载优化**：
  - 图片/附件批量下载使用 Promise.allSettled，单个失败不影响整体。
  - 本地缓存目录可选，便于调试与离线查看。
- **资源管理增强**：
  - **新增** 定时器资源泄漏防护：animationTimer 和 toolTimer 在 finally 块中确保正确清理
  - **新增** 类型安全的统计计算：改进 token 统计的类型断言和边界检查
  - **新增** 一致的错误处理：统一的异常捕获和资源释放机制
- **分卡策略优化**：
  - **新增** CardKitReply 自动分卡：正文超过 10000 字符时在安全块边界切分，避免单卡过大
  - **新增** 分卡串行化：避免并发旋转导致的竞态条件

## 故障排查指南
- WebSocket 连接问题：
  - 检查握手超时与 ping 超时配置，关注 onReconnecting/onReconnected/onError 日志。
  - 确认 appId/appSecret/source 配置正确。
- 消息归一化失败：
  - 检查 normalize 参数（botIdentity、stripBotMentions、includeRaw）。
  - 确认消息结构符合预期。
- 卡片回调超时：
  - 使用底层 WSClient 方式，handler 返回值原样进 ACK，避免高层封装吞事件。
  - 授权卡回调需在上层 PermissionBroker 中校验管理员身份。
- 卡片更新失败：
  - 优先按 messageId 更新，失败回退到 token 更新。
  - 流式模式可能被官方关闭，CardKitStream 会自动重试。
- **ReplyParts 相关问题**：
  - **新增** 检查精简模式是否正确回收：确认新正文段出现时旧内容被清空
  - **新增** 验证工具段滚动：确认新工具出现时上一个工具段被置空
  - **新增** 调试终态组装：检查 composeFinal() 返回的内容是否符合预期
- 图片/附件下载失败：
  - 检查资源类型与 fileKey，确认缓存目录存在且可写。
  - 兼容不同 SDK 返回结构（Buffer、ReadableStream、writeFile）。
- 会话中断与恢复：
  - 确认 ConversationManager 的 persistSessionFile 在事件中被调用。
  - 检查 sessionFile 是否成功落盘与映射持久化。
- **资源泄漏问题**：
  - **新增** 检查定时器是否正确清理：确认 animationTimer 和 toolTimer 在 finally 块中释放
  - **新增** 监控内存使用情况：定期检查是否存在未释放的定时器句柄
  - **新增** 验证错误路径：确保异常情况下资源仍能正确释放

## 结论
消息桥接层通过 LarkTransport 与 FeishuAgentBridge 协同工作，实现了飞书消息到智能体会话的高效转换。**最新的 ReplyParts parts-based 架构**完全替代了临时文本机制，提供了更强大的回复管理能力，支持精简模式滚动回收和详细模式全量保留。借助 ConversationManager 的会话队列与中断机制、CardKitReply 的智能分卡与流式渲染、CardKitStream 的高性能卡片更新、MessageStore 的去重与失败保护，系统在高并发与不稳定网络环境下仍能提供稳定可靠的交互体验。**最新改进包括 ReplyParts 架构重构、CardKitReply 分卡策略优化、关键资源泄漏防护、类型安全的统计计算和一致的错误处理机制**，进一步提升了系统的稳定性和可靠性。同时，通过管理员校验、文件名清洗与指令限制等措施，保障了安全性与可控性。
